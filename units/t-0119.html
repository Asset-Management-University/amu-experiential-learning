The code that never complained

T1: The Ache

You are Onalenna, asset manager at Corathyl Water Treatment Works, and you have just done something clever. Instead of working out the depreciation of every asset in the register by hand - hundreds of them - you wrote a short piece of code to do it. You ran it. No errors, no complaints, just a tidy column of numbers. You dropped them straight into the annual report.

Weeks later, someone queries a single figure. You look at it, and your stomach drops.

Because the code never complained, you have no idea how many of those hundreds of numbers are wrong. Not one thing warned you. The programme did not crash; it did not turn red; it did not hesitate. It simply produced confident, tidy, wrong answers - and you cannot check them by hand, because avoiding that was the whole point of writing the code. You trusted it for one reason only: it ran. And you now see, far too late, that running and being right are not the same thing at all.

My code ran perfectly and gave me hundreds of numbers I cannot check by hand - and one of them was wrong. How do I ever know that the code I write is actually CORRECT, and not just quietly confident?

Before you read on, decide. The code ran. No error, no warning, nothing to suspect — and it produced depreciation figures for every asset in the register, which is exactly why you wrote it, because doing that by hand was impossible. The report went out. Somebody in finance found the wrong number: an asset entered with a life of zero, where the arithmetic quietly returned a nonsense value instead of refusing, and the nonsense flowed straight through into the total. The code is not sloppy. Write down how you would ever know that code you write is actually correct — your own answer, not a shortlist to choose from.

Now compare — the five answers, and where the expected answer has to come from

• “Check a few rows by hand.” You did, near enough, and they were right — because the rows you would pick by hand are the ordinary ones. The wrong answer was in an input you would never have thought to look for, which is the whole reason it survived.

• “Have a colleague read the code.” Worth doing and it catches a different class of fault. A reviewer reads the code you wrote for the cases you were thinking about; the zero life was not a coding mistake so much as a case that never crossed anybody's mind.

• “Add error handling so nothing can crash.” The exactly wrong lesson from this failure. It crashing would have saved you. What hurt was that it did not crash — it returned something plausible and kept going.

• “Print the results and eyeball them for anything odd.” On hundreds of figures nobody can hold in their head, this finds only the obviously mad ones, and a plausible-looking wrong number is by definition not one of those.

• “Compare this run against the last one and check nothing changed.” Useful for catching regressions, and it is circular as proof of correctness: it establishes only that the code still does what it did before, which is what you are trying to question.

• What you need is a set of small automatic checks that state what the answer must be, independently of the code. Everything turns on where that expected answer comes from: it must be worked out by hand, before the code runs — a cost of R1,200,000 over six years is R200,000 a year, and you know that without executing anything. Write the check by asking the code what it currently produces and you have proved only that it agrees with itself. Then aim them where the silent wrong answers actually live: the awkward inputs nobody pictures while writing — the zero, the negative, the salvage larger than the cost. And notice what the checks encode besides a number: for a bad input the correct behaviour is to refuse loudly, not to return something plausible, because a nonsense value that flows quietly into a report is far worse than a failure at your desk. Which is the reframe: a failing check is the tool working. This one would have taken seconds and cost you nothing but a moment's embarrassment in private.

There is a small, almost embarrassingly simple habit that answers this - and it is the same one used to prove the software that flies aeroplanes. Let us show you one - finished - first.

T2: The Tool in Action

Here is the one page that would have saved the report - a small set of automatic checks that prove the depreciation code, and catch the bug in seconds.

1. The function under test - what exactly are you proving?

The function under test: calculate_depreciation(cost, life, salvage) - the straight-line depreciation used for every asset in the register. One small function doing one job you can state in a single sentence. That is what a unit test proves: one unit, one behaviour.

2. The known-answer case - worked out BY HAND, first

Pick an input whose answer you work out INDEPENDENTLY, by hand. A R1,200,000 asset over 6 years with no salvage: (1,200,000 - 0) / 6 = R200,000 a year. You know that before you run a single line. A second case, with salvage: (1,200,000 - 120,000) / 6 = R180,000.

3. The edge cases - the awkward inputs everyone forgets

The awkward inputs. What if the life is 0? The bare formula divides by zero and returns infinity - a nonsense number that would flow silently into the report. A sound function must RAISE an error there, not return nonsense. Also worth testing: negative values, and a salvage larger than the cost.

4. The assertion and the run - expected versus actual

assert calculate_depreciation(1200000, 6, 0) == 200000 - expected versus actual, checked automatically. Run them: '2 passed, 1 FAILED'. The failure is the zero-life case - and that failure is the test WORKING. It caught a dangerous bug in seconds, at your desk, instead of in the annual report.

5. Re-run forever - the safety net (regression)

After EVERY change, run the whole set again. Fixing the zero-life guard must not quietly break the salvage calculation - and only re-running everything proves it did not. That is regression testing: the safety net that lets you change your code with confidence instead of dread.

Look at the last line: 2 passed, 1 FAILED. It is tempting to read that as bad news. It is the opposite. That failure is the test doing its job - it found a real, dangerous bug (a division by zero that would have put nonsense into the annual report) while Onalenna was still sitting at her desk, with nobody watching and nothing at stake. A test that fails at your desk has just saved you from a test that fails in front of your director. Now let us walk through how it works.

T3: The Blueprint

What you just saw is a unit test: a small automatic check that runs one piece of your code against an answer you already know is right. Think of it as the jig on a factory bench - the simple gauge a part is dropped into to prove it is within tolerance before it ever goes into an engine. Each part answers a question:

  • What exactly am I proving? One small function doing one job you can say in a sentence. That is the "unit" in unit test - you are not proving the whole system at once, you are proving one honest piece of it.
  • How do I know the right answer? You choose a known-answer case - an input simple enough that you can work the answer out by hand, on paper, before you run anything. A R1,200,000 asset over 6 years is R200,000 a year. You knew that without the computer, and that is precisely what makes it proof.
  • How do I check it automatically? With an assertion - one line that says "the answer I expect must equal the answer you produced", and which complains loudly if it does not. That single line is the whole mechanism.
  • What about the awkward inputs? Those are the edge cases: zero, negative numbers, the boundary, the invalid input. They are where real bugs live. A life of zero years should refuse - raise an error - not quietly return infinity. A function is judged by how it handles the strange inputs, not the easy ones.
  • How do I know my fix did not break something else? You re-run every test after every change - regression testing. It is the safety net that lets you change code confidently instead of fearfully.

One rule sits above all the others, and it is the line between real testing and fooling yourself: work the expected answer out independently - never by running the code and pasting whatever it printed. If you copy the code's own output into the test, you have not proved the code is right; you have only frozen whatever it already does, bug and all. The test must know the answer before the code speaks.

Does it scale? The small automatic check Onalenna writes to prove her depreciation sum follows the exact principle used to validate the software that flies an airliner: a known input must produce a known, correct output, every single time - or the system is not considered safe to trust.

T4: Your Turn

Now prove a function of your own. Here is a small one every asset engineer uses - availability:

availability = uptime / (uptime + downtime)

  1. Write the known-answer case. Pick an input you can check on paper - say 90 hours running and 10 hours down. Work out the answer by hand first, then write the assertion.
  2. Write an edge case. What if uptime and downtime are both zero - a machine that has not been installed yet? The bare formula divides by zero. Decide what the function should do (refuse and raise an error, most likely), and write the test that holds it to that.
  3. Say what a failure would tell you. One sentence: if this test goes red, what have you learned?

Check yourself: 90 / (90 + 10) = 90 / 100 = 0.90 - availability of 90%. You knew that before touching the keyboard, which is exactly why it can serve as proof.

T5: The Guardrails

Testing is simple, but a few traps catch almost everyone the first time. Glance through these before you trust a green tick.

The common traps - and how to dodge them

• The cop-out. Running the code first and pasting its output in as the "expected" answer. This proves nothing at all - it only freezes today's behaviour, bug included. Work the answer out independently, or you have not tested anything.

• The happy-path illusion. Testing only the neat, sensible inputs and assuming the awkward ones will be fine. Zero, negative, empty and invalid inputs are exactly where the real bugs hide.

• "It ran, so it works." The silent danger, and the one that caught Onalenna. Code that crashes tells you something is wrong; code that quietly returns a confident wrong number tells you nothing.

• The one-and-done. Never re-running the tests after a change, so a fix in one place silently breaks something that used to work. Run the whole set, every time.

• Testing the machinery instead of the result. Checking that a loop ran five times rather than that the final answer is correct. Test the behaviour you actually care about, not the internal plumbing - the plumbing is allowed to change.

Onalenna's code never complained - and that was precisely the problem. Now you hold the habit that makes silence trustworthy: state what the answer should be before you run anything, check it automatically, hunt the awkward inputs, and re-run everything after every change. Do that, and you will stop hoping your numbers are right and start being able to prove it - which, when hundreds of decisions rest on those numbers, is the whole of the job.
