T1: The Ache

It is a Tuesday morning at the Tank You yard in Nethmora View. You are at the small office desk - the one with the wobbly leg - a mug of rooibos going cold beside the keyboard. Ibraaheem drops a printout in front of you: every repair the fleet has had this year - the old bakkie, the Nissan, the truck. He taps the page with one finger.

"The old bakkie broke down again on Saturday. That is the third time. Muhammad thinks we should sell it. I think it is fine. Just tell me - which vehicle is actually costing us the most?"

The printout is 487 rows long. Each row is one job: a date, which vehicle, what broke, and the rand cost. Some costs are blank. Some dates are typed three different ways. One row says "R 3 200", another "3200.00", another just "see invoice". Ibraaheem is standing there waiting, and there is a delivery run leaving in forty minutes. You reach for the obvious move - open the spreadsheet, scroll, and add the numbers up by eye, vehicle by vehicle. But you did exactly that last month on a smaller list and got it wrong: you double-counted a row, missed three blanks, and the figure you gave Ibraaheem was off by nearly R5,000. He noticed. You felt small.

Which vehicle is actually costing us the most - and how do I get an answer I can trust, and repeat next month, instead of guessing off a messy page and getting it wrong?

Before you read on, decide. You need to know which vehicle is costing the most. The data is a messy export: blank rows, the same vehicle written three ways, duplicated lines. You did this by hand last month on a shorter list — double-counted a row, missed three blanks, and gave Ibraaheem a figure that was out by nearly R5,000. He noticed. And you will have to do it again next month, and the month after. Write down how you would get an answer you can trust — your own answer, not a shortlist to choose from.

Now compare — the five answers, and what “doing it more carefully” cannot fix

• “Be more careful this time. Check it twice.” The answer that already failed, offered again with more effort behind it. And it does not survive next month, when the list is longer and you are busier.

• “Get somebody to check my figures.” Two people who can each make a mistake, on a list neither of them can hold in their head. It also costs somebody else’s morning, every month, for ever.

• “Tidy the spreadsheet properly first, then total it.” The right instinct — cleaning is genuinely most of the work — and done by hand it is undone the moment next month’s export arrives with the same three spellings.

• “Buy a system that reports this automatically.” It will report from whatever it is given, and what you are being given is the mess. The cleaning does not disappear; it moves somewhere you can no longer see it.

• “Only count the big vehicles — near enough for a decision.” That answers a smaller question quickly, and it cannot be defended when Ibraaheem asks why one is missing.

• The problem is not your care; it is that the work is being done by hand at all. Write the cleaning and the totalling down as steps a machine performs — the same steps, in the same order, every time — and three things change at once. The answer becomes repeatable: next month is one button, not a morning. It becomes checkable, because the steps are written down and somebody can read what you actually did rather than trusting the total. And when a rule turns out to be wrong — the fourth spelling of a registration nobody had seen — you fix it once, in the open, and every future month inherits the fix. Keeping a record of what changed and why is part of the answer, not admin: it is the difference between a number you can defend and a number you can only assert.

You do not need a better guess. You need a reliable, repeatable way to read a messy asset dataset, clean it, total the cost per vehicle, and show it in a chart - so that next month, and the month after, you press one button and trust the number. Here is how.

T2: The Tool in Action

A spreadsheet is fine for ten rows and dangerous for five hundred: scrolling and eyeballing does not scale, and it cannot be checked. What you need is a small set of free tools that read the data the same way every time and keep a record of every change - Python (plain-English instructions the computer runs in order), pandas (a Python add-on built for tables), matplotlib (for the chart), and Git (a logbook that snapshots your work). Watch them answer Ibraaheem's question on the real Tank You log.

Step 1 - Set up a version-controlled workspace

mkdir tank-you-analysis and cd into it; python -m venv .venv, then activate it (your terminal line now starts with (.venv)); pip install pandas matplotlib lands them inside the toolbox, not all over the machine; git init; a .gitignore holding one line, .venv/; git add .gitignore and git commit -m 'Start project'. The toolbox is clean and the logbook is open.

Step 2 - Read the data

In analyse.py: import pandas as pd; orders = pd.read_csv('work_orders_2026.csv'); print(orders.shape). Run it - it prints (487, 4): 487 repair jobs, 4 columns (date, asset, fault, cost_rand). git commit -m 'Read the work-order CSV'.

Step 3 - Look, then clean (the clipboard, not the gut - in code)

orders['cost_rand'].isna().sum() prints 31 blanks; by eye the column is text - 'R 3 200', '3200.00', 'see invoice'. Strip 'R' and spaces, then pd.to_numeric(..., errors='coerce') turns 'see invoice' into a blank - now 34 (31 + 3). Drop them: priced = orders.dropna(subset=['cost_clean']) leaves (453, 5) rows (487 - 34 = 453). The 34 is honest and you can defend it. git commit -m 'Clean the cost column, drop 34 rows with no cost'.

Step 4 - Answer the question

priced.groupby('asset')['cost_clean'].sum().sort_values(ascending=False) prints: bakkie_old R48,920; bakkie_new R21,340; truck R18,075. There it is - the old bakkie has cost R48,920 in repairs this year, more than the newer two put together. Muhammad was right: the numbers, not the sentiment about the family bakkie, say its repair bill now outruns what a newer vehicle would cost to run.

Step 5 - Chart it and commit (reproducible: one button next month)

import matplotlib.pyplot as plt; by_asset.plot(kind='bar'); plt.title('Tank You - repair cost per asset, 2026'); plt.ylabel('Cost (rand)'); plt.tight_layout(); plt.savefig('cost_per_asset.png'). Then git add analyse.py cost_per_asset.png and git commit -m 'Chart cost per asset'. Next month you change one thing - the file - and press one button.

See what the five steps did. They turned a messy 487-row page into a defensible answer - the old bakkie, R48,920, more than the newer two together - reached the same way every time, with an honest, auditable trail (the 34 unpriced rows named and set aside, every change snapshotted in Git). And notice the deeper lesson the number carries: an old, high-kilometre asset can quietly cost more to keep limping along than a newer one would cost to run. Muhammad's gut said sell it; the data did not overrule his feeling - it gave it a backbone he can defend to a bank or a brother. This is not coding for its own sake. It is the power to find the truth in your own numbers, and stand behind it.

T3: The Blueprint

You build the answer in five moves.

  • 1. Set up a versioned workspace. A project folder; a venv (a clean toolbox holding just this job's tools); the tools installed inside it; and git init to start a logbook. Snapshot.
  • 2. Read the data. Pull the file into a pandas DataFrame (a table steered by commands); check its shape.
  • 3. Look, then clean. Inspect first; count the blanks; strip the mess; turn the column into real numbers so bad text becomes an honest blank; drop the rows with no cost, on purpose.
  • 4. Answer the question. Group by vehicle, sum the cost, sort biggest first.
  • 5. Chart and commit. Draw it, save it, snapshot it - so it re-runs itself next month.

The ideas underneath: a venv keeps one project's tools fenced off so they never tangle with your whole machine (if it breaks, you throw the toolbox away and rebuild); errors="coerce" is the honest move - text that cannot be a number ("see invoice") becomes a blank you handle on purpose, rather than a crash or a silent wrong total; and a Git commit is a dated snapshot with a note ("cleaned the cost column"), so you can always walk back and always answer "what did you change since last month?". This fits any time you have asset data in a file - work orders, meter readings, fuel logs - and need an answer you can defend and repeat; it is overkill for ten rows you will never look at again.

T5: The Guardrails

A few lines keep your analysis honest.

The traps - and how to stay true

• Do not eyeball a long list. Five hundred rows will hide a double-count or a missed blank every time - that is how you end up off by R5,000. Let the code add up, the same way every time.

• Do not delete the mess silently. Count what you drop and say why ("34 rows with no cost"). A number you cannot account for is a number no one should trust.

• Do not install tools all over your machine. Use a venv per project, or two jobs will fight over versions and one day nothing runs. A clean toolbox you can throw away is the whole point.

• Do not work without commits. Hours of un-snapshotted work is one wrong keystroke from gone. Commit at each real step; the logbook is cheap and the regret is not.

• Do not let the tool become the goal. The aim is a trustworthy answer to a real question, not a clever script. If a calculator settles it faster, use the calculator.
